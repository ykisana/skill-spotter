# How skill-spotter chose its matcher

skill-spotter has to decide, after every Claude Code turn, whether this turn is "the same task" as earlier ones. It has to do that in about 40 ms, with no network and no tokens, and it should rarely suggest something that isn't really a repeated task. Rather than pick a method by intuition, we built a lab to measure the options.

## The data

There's no public dataset of "Claude Code turns labelled by task", so we generated one, at development time only and never from user data:

- **98 task families** in 14 areas (git, releases, deploys, migrations, MCP tools, mobile builds…). Each family has an action trace template, 10 phrasings across five difficulty tiers, and 4 *hard negatives*: lookalike tasks that share words or commands but differ ("deploy to staging" vs "roll back staging").
- **5,208 one-off turns**, about five for every repeated turn, because most real turns never repeat.
- **Action traces generated by code**, with realistic noise: exploration, retries, reordered steps, subagents.
- **A 75-day timeline** of sessions in 11 projects, so the whole product can be *replayed*, with the real trigger rule, caps and snoozing.

116 headless Claude calls (about $6.50) produced it. Every reply is cached, so the dataset rebuilds without new calls.

## The candidates

| Category | Candidates |
|---|---|
| Command templating | Hand rules, Drain, Drain3, entropy-based position typing, Fig autocomplete specs, LogLSHD-style LSH grouping |
| Text | Word n-gram Jaccard, TF-IDF (word and char), BM25, MinHash, SimHash, Model2Vec, 7 small embedding models |
| Actions | Weighted Jaccard (with/without IDF, meaningful-only), TF-IDF over templates, template embeddings, sequence edit distance / LCS / DTW, file overlap |
| Fusion | The rule, linear, logistic regression (plain and monotone), gradient-boosted trees |
| Clustering | Online leader, connected components, agglomerative (average/complete), DBSCAN, HDBSCAN, Louvain, k-means reference |
| Lookup | Brute force, inverted index, MinHash LSH, hnswlib, FAISS, sqlite-vec |
| Sequences | Contiguous n-grams, gapped n-grams, PrefixSpan, SPADE |

## What we learned

1. **Pairwise scores lie if the negatives are easy.** The first run had pairwise PR-AUC about 0.99 everywhere, yet replay precision was about 0.6. The negatives rarely shared a command, but one-offs in real use often do (three different `psql -c` questions). Adding "same command, different task" negatives made the benchmark tell methods apart.
2. **Exploration isn't evidence.** Two different questions answered with only Grep looked identical to the matcher. Counting only meaningful actions fixed most false suggestions: precision went from 0.67 to 0.90.
3. **Learned models learn your generator.** A logistic regression with timeline features learned that "same session" means "different task", because synthetic repeats were spread across sessions. Another learned to *penalise* word overlap, because synthetic repeats were paraphrased. Both looked best on paper and would have failed real users, rejecting identical repeats. Scenario tests on the shipped model caught both. The fix was to drop timeline features and constrain similarity weights to be non-negative.
4. **Simple beats fancy here.** Small embedding models help text similarity (jina-small PR-AUC 0.56 vs BM25 0.49), but actions carry most of the signal. A stdlib model reaches test precision 1.0 and recall 0.97 in replay. Batch clustering (HDBSCAN, agglomerative) found no extra tasks and created duplicate suggestions, so the background tier only merges patterns.
5. **Live sessions still surprise.** Paraphrased questions with no meaningful actions don't match, and a single-edit step phrased very differently can split. These are documented limitations, to be tuned on real labelled data.
